# WikiVibe для macOS: контракты серверной интеграции

[English](BACKEND_SPEC.en.md) · [Русский — каноническая спецификация](BACKEND_SPEC.md) · [简体中文](BACKEND_SPEC.zh-CN.md)

Статус: **BLOCKED**. Серверные решения принимает команда backend. Документ охватывает вход в нативное приложение macOS, баланс и расходы аккаунта, а также HTTPS-переход к пополнению. Настройка агентов и платежи внутри приложения в объём не входят. При расхождении переводов приоритет имеет русская спецификация.

## Подтверждённые публичные наблюдения

- `https://auth.wikivibe.dev/` возвращает одностраничное HTML-приложение. Открытие страницы не создаёт сессию настольного клиента.
- Проверенные адреса обнаружения сервисов и документации возвращали HTML, а не подтверждённый JSON-контракт OIDC/OpenAPI.
- `GET https://auth.wikivibe.dev/api/v1/auth/me` без учётных данных вернул HTTP 401 и `{"code":"UNAUTHORIZED","message":"Authorization header is required"}`. Схема успешного ответа и допустимые учётные данные настольного клиента не подтверждены.
- `GET https://auth.wikivibe.dev/api/v1/auth/sso/config` вернул конфигурацию браузерного SSO: issuer `https://auth.wikivibe.dev`, перенаправления для `api.wikivibe.dev` и `dev.wikivibe.dev`. Это не регистрация клиента macOS.
- `GET https://api.wikivibe.dev/v1/usage?days=7` без учётных данных вернул HTTP 401 и `{"code":"API_KEY_REQUIRED","message":"Требуется API-ключ"}`. В этом методе клиент из справочного проекта использует API-ключ Bearer. Метод нельзя считать API для сессии аккаунта.
- Повторное исследование действующего клиента подтвердило PKCE S256 и проверку `state` в браузерном SSO. Это подтверждение браузерного механизма, а не регистрация настольного клиента.

## Повторное исследование действующего клиента

Проверены публичные scripts, отрисованный `/docs` и минимальные GET-ответы без извлечения browser storage, cookies, API-ключей или Authorization. Вход, создание ключей, inference и платежи не выполнялись.

Публичный loopback `tfcli` в script относится к импорту настроек API-ключей из `/keys`, не является подтверждённым desktop account login и не используется здесь. Поиск публичной документации не дал регистрации macOS-клиента. Отсутствие такой информации в проверенных источниках не доказывает, что backend не может её предоставить.

**Точный внешний prerequisite:** backend должен предоставить разрешённый публичный desktop `client_id`, callback/loopback и правила портов (либо device flow), применимость code exchange к этому клиенту, audience/scopes и успешные безопасные JSON-схемы аккаунта/денег. Для refresh/logout нужны сроки, ротация, конечные ошибки и отзыв текущей сессии. Необходимы precision/null, период/timezone, принадлежность данных аккаунту и лимиты опроса. Без этого нельзя получить legitimate desktop session, поэтому Keychain restore, refresh/logout, реальные суммы, polling/stale/late-response transitions остаются BLOCKED. Подтверждённый переход к пополнению реализован независимо.

## 1. Вход через системный браузер

Назначение: создать сессию аккаунта для нативного публичного клиента без ввода пароля в приложении и без встроенного client secret. Ответственный: backend.

**Действующий метод для настольного клиента не подтверждён.** Нужно опубликовать HTTP-метод, URL, параметры и схему успешного ответа. Приложение не вызывает ни один из предложенных ниже маршрутов или сценариев.

**Предложение, не действующий API:** Authorization Code с PKCE (S256). Зарегистрировать публичный клиент и один разрешённый механизм возврата: HTTP loopback на localhost с согласованными правилами выбора порта либо защищённый зарегистрированный callback. Если поддерживается только авторизация устройства, опубликовать её вместо OAuth callback.

Определить поля запроса авторизации: `client_id`, `redirect_uri`, `response_type`, scopes, `state`, `code_challenge` и `code_challenge_method`. При возврате передавать одноразовый `code` и исходный `state` либо именованную ошибку. Для POST-обмена кода на токены определить тип содержимого и поля `grant_type`, `client_id`, `code`, `redirect_uri`, `code_verifier`.

Предлагаемая схема ответа с токенами: `access_token: string`, `token_type: "Bearer"`, `expires_in: integer seconds > 0`, `refresh_token?: string`, `scope?: string`. Подтвердить реальные названия, структуру оболочки ответа и правила для необязательных полей и `null`. Токены хранятся только в macOS Keychain. Ключ inference API не является токеном аккаунта или токеном обновления.

Определить отмену, неверные state/redirect/code, истёкший или повторно использованный код, тайм-аут, HTTP 400/401/403/429/5xx, бизнес-коды ошибок, безопасные сообщения пользователю и Retry-After. Указать срок жизни кода, ограничения попыток и защиту от повторного использования. До успешного обмена и подтверждения аккаунта приложение остаётся неавторизованным, даже если браузер открылся.

## 2. Аккаунт, восстановление, обновление и выход

Назначение: определить владельца сессии и её жизненный цикл. Ответственный: backend.

Наблюдавшийся GET `/api/v1/auth/me` не подтверждает схему успешного ответа. Нужны host, path, method и схема авторизации. Предлагаемый ответ об аккаунте: стабильный несекретный `account_id: string`, `display_name?: string`. Определить оболочку ответа и минимальные scopes. В примерах не должно быть реальных персональных данных.

Обновление: подтвердить POST-метод, схему запроса, единицы срока действия, правила ротации, аннулирование предыдущего refresh token и обработку параллельных или повторных запросов. Предложение: запрос `refresh_token: string`, ответ по указанной выше схеме токенов. Указать срок жизни refresh token и конечную ошибку истёкшей или отозванной сессии.

Выход и отзыв: подтвердить адрес, HTTP-метод, авторизацию, схемы запроса и ответа, отзыв только текущей сессии, отличие от отзыва всех сессий и идемпотентность. Локальный выход должен удалять запись Keychain и отменять незавершённые запросы даже при недоступном сервере. Серверный отзыв нельзя выдумывать. Ошибка чтения Keychain не означает отсутствие или истечение срока действия учётных данных.

Граница поколений сессии: ответ запроса предыдущей сессии не должен применяться после выхода или смены аккаунта. Нужны стабильный идентификатор аккаунта и способ проверить принадлежность полученных данных.

## 3. Баланс и расходы аккаунта

Назначение: получать реальные денежные значения и расходы с сервера, а не вычислять их по локальным журналам агентов. Ответственный: backend.

**Маршруты браузерного account API обнаружены, но успешные JSON-схемы и применимость к desktop-сессии не подтверждены.** Уточнить `/user/profile` и `/usage/stats` вместо создания второго неподтверждённого API. Метод `/v1/usage?days=7`, защищённый API-ключом, не подставляется вместо них. Подтвердить scopes и совместимость с авторизацией по сессии настольного клиента.

**Предложение схемы, не действующий API:**

```json
{
  "account_id": "example-account",
  "as_of": "2026-10-13T12:00:00Z",
  "balance": { "amount_minor": 0, "currency": "USD", "scale": 2 },
  "expenses": {
    "amount_minor": 0,
    "currency": "USD",
    "scale": 2,
    "scope": "account",
    "period_start": "2026-10-01T00:00:00Z",
    "period_end": "2026-11-01T00:00:00Z"
  }
}
```

Вместо целых чисел в минимальных денежных единицах можно выбрать десятичные строки, но контракт должен однозначно задать точность, валюту, отрицательный баланс, округление, отсутствие полей, `null` и числовые пределы. `0` — реальный ноль; отсутствие поля не означает ноль. Указать область аккаунта или ключа, даты UTC ISO-8601, включительность границ периода, часовой пояс расчёта расходов и время актуальности данных. Снимок данных должен быть согласован для одного аккаунта и одного момента времени.

Определить HTTP- и бизнес-семантику: 401 для истёкших или отозванных учётных данных; 403 для ошибок прав или scopes; 429 с Retry-After; 5xx и временные сетевые ошибки; бизнес-ошибки внутри HTTP 200, если используется оболочка ответа. Указать версию схемы и обязательные поля. При сетевой ошибке сохранять последнюю подтверждённую сумму с временем получения и отметкой об устаревании. Без успешного запроса суммы не показываются.

Опрос: опубликовать минимальный интервал, лимиты запросов и правила кэширования/ETag. Если рекомендаций нет, предложение — раз в 60 секунд при активной подтверждённой сессии, не более одного запроса одновременно. При выходе опрос прекращается, старый запрос отменяется, его ответ не принимается. Ручное обновление соблюдает серверные ограничения.

## 4. HTTPS-переход к пополнению

Назначение: открыть официальный браузерный сценарий без создания платежа приложением. Ответственный: backend.

**Подтверждённый URL:** `https://api.wikivibe.dev/purchase`. Публичная документация и router определяют его как пополнение; фактическая навигация проверена без оплаты. Страница требует входа в браузере. Приложение открывает только этот фиксированный HTTPS URL, без токенов или session binding в query. Открытие страницы не подтверждает вход в приложение и не означает выполненный платёж.

## Минимальный порядок подключения

1. Публичный настольный клиент, возврат из браузера, обмен кода на токены и безопасная схема ошибок.
2. Идентификатор аккаунта, сроки действия, обновление токенов и отзыв отдельной сессии.
3. Схема баланса и расходов: единицы, период и правила опроса.
4. Использовать подтверждённый `https://api.wikivibe.dev/purchase`, не создавая платёж.
5. Пользователь входит самостоятельно. Проверяются возврат, восстановление после перезапуска, реальные суммы, обновление, отсутствие сети и устаревшие данные, истечение сессии, выход и переход к пополнению без платежа. Доступ к чужим учётным данным для проверки не требуется и не допускается.
