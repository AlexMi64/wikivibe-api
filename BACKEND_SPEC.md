# WikiVibe для macOS: контракты серверной интеграции

[English](BACKEND_SPEC.en.md) · [Русский — каноническая спецификация](BACKEND_SPEC.md) · [简体中文](BACKEND_SPEC.zh-CN.md)

Статус: **вход реализован; баланс и расходы вне объёма.** Серверные решения принимает команда backend. Документ охватывает вход в нативное приложение macOS, баланс и расходы аккаунта, а также HTTPS-переход к пополнению. Настройка агентов и платежи внутри приложения в объём не входят. При расхождении переводов приоритет имеет русская спецификация.

Вход, восстановление сессии, обновление токена и выход реализованы и описаны как действующий контракт (разделы 1, 1a и 2). Баланс и расходы — предложение для следующего этапа: приложение их не запрашивает и не показывает.

## Подтверждённые публичные наблюдения

- `https://auth.wikivibe.dev/` возвращает одностраничное HTML-приложение. Открытие страницы не создаёт сессию настольного клиента.
- Проверенные адреса обнаружения сервисов и документации возвращали HTML, а не подтверждённый JSON-контракт OIDC/OpenAPI.
- `GET https://auth.wikivibe.dev/api/v1/auth/me` без учётных данных вернул HTTP 401 и `{"code":"UNAUTHORIZED","message":"Authorization header is required"}`. Схема успешного ответа и допустимые учётные данные настольного клиента не подтверждены.
- `GET https://auth.wikivibe.dev/api/v1/auth/sso/config` вернул конфигурацию браузерного SSO: issuer `https://auth.wikivibe.dev`, перенаправления для `api.wikivibe.dev` и `dev.wikivibe.dev`. Это не регистрация клиента macOS.
- `GET https://api.wikivibe.dev/v1/usage?days=7` без учётных данных вернул HTTP 401 и `{"code":"API_KEY_REQUIRED","message":"Требуется API-ключ"}`. В этом методе клиент из справочного проекта использует API-ключ Bearer. Метод нельзя считать API для сессии аккаунта.
- Повторное исследование действующего клиента подтвердило PKCE S256 и проверку `state` в браузерном SSO. Это подтверждение браузерного механизма, а не регистрация настольного клиента.

## Повторное исследование действующего клиента

Проверены публичные scripts, отрисованный `/docs` и минимальные GET-ответы без извлечения browser storage, cookies, API-ключей или Authorization. Вход, создание ключей, inference и платежи не выполнялись.

Публичный loopback `tfcli` в script относится к импорту настроек API-ключей из `/keys`, не является подтверждённым desktop account login и не используется здесь. Поиск публичной документации не дал регистрации macOS-клиента. Отсутствие такой информации в проверенных источниках не доказывает, что backend не может её предоставить.

**Регистрация desktop-клиента выполнена.** В `origin/main` серверной части добавлен четвёртый клиент `desktop` (`shared_auth.desktop_redirect_uri`, по умолчанию `http://127.0.0.1/callback`). Валидатор принимает для него любой loopback-порт (RFC 8252 §7.3), но только зарегистрированные схему, хост и путь; `client_id` связан с этим адресом через `ResolveClient`. Баланс и расходы в текущий объём не входят, поэтому их контракты ниже остаются предложением.

## 1. Вход через системный браузер

Назначение: создать сессию аккаунта для нативного публичного клиента без ввода пароля в приложении и без встроенного client secret. Ответственный: backend.

**Действующий метод: Authorization Code + PKCE S256.** Реализовано и проверено:

- `GET https://auth.wikivibe.dev/api/v1/auth/sso/authorize` с `client_id=desktop`, `redirect_uri=http://127.0.0.1:<порт>/callback`, `state`, `code_challenge`, `code_challenge_method=S256`.
- Без центральной сессии браузера отвечает `302` на `https://auth.wikivibe.dev/login?redirect=…`; с сессией — `302` на зарегистрированный callback с `code` и исходным `state`.
- `POST https://api.wikivibe.dev/api/v1/auth/sso/token` с JSON `{client_id, redirect_uri, code, code_verifier}` возвращает `access_token`, `refresh_token`, `expires_in` (секунды), `token_type` и `user`. `grant_type` и `response_type` не используются.
- Неверный `client_id`/`redirect_uri` — `400 INVALID_REQUEST`; неверный `code_verifier` — `INVALID_CODE_VERIFIER`.

`state` обязателен, не длиннее 512 байт и состоит из видимых ASCII. `code_verifier` — 43…128 символов base64url. Токены хранятся только в macOS Keychain; ключ inference API не является токеном аккаунта или токеном обновления.

## 1a. Жизненный цикл сессии

Реализовано и проверено: `POST https://api.wikivibe.dev/api/v1/auth/refresh` с JSON `{refresh_token}` возвращает `access_token`, `refresh_token`, `expires_in`, `token_type`; `refresh_token` ротируется, поэтому приложение сохраняет полученный. `POST https://api.wikivibe.dev/api/v1/auth/logout` с `{refresh_token}` отзывает только этот refresh token — отдельно от отзыва всех сессий аккаунта. `GET https://api.wikivibe.dev/api/v1/auth/sso/me` с `Bearer` подтверждает аккаунт и возвращает `401`, если сессия отозвана. Ошибки `401`/`403` приложение трактует как истёкшую сессию, а не как сетевой сбой.

## 2. Аккаунт, восстановление, обновление и выход

Назначение: определить владельца сессии и её жизненный цикл. Ответственный: backend. **Реализовано.**

Аккаунт: `GET https://api.wikivibe.dev/api/v1/auth/sso/me` с `Bearer` возвращает `{user, telegram_user}` в стандартной оболочке `{code, message, data}`. Приложение читает из `user` только `id`, `username` и `email` — этого достаточно, чтобы показать, кто выполнен, и ничего лишнего не сохраняется. Оболочка авторитетна: `code != 0` — ошибка даже при HTTP 200.

Обновление: `POST /api/v1/auth/refresh` с `{refresh_token}`; ответ `{access_token, refresh_token, expires_in, token_type}`. Refresh token ротируется — приложение сохраняет полученный, иначе следующее обновление упало бы как отозванное. `expires_in` переводится в абсолютное время истечения при получении, а не хранится как длительность.

Выход и отзыв: `POST /api/v1/auth/logout` с `{refresh_token}` отзывает только этот токен (не все сессии аккаунта, в отличие от `/auth/revoke-all-sessions`). Локальная сессия удаляется из Keychain до серверного вызова и независимо от его результата: недоступный сервер не должен оставлять пользователя в системе, из которой он вышел.

Восстановление: при запуске приложение читает сессию из Keychain. Если access token истёк — обновляет; если refresh token отозван (`401`/`403`) — выходит из аккаунта и показывает, что вход не выполнен. Сетевая ошибка не считается выходом: сессия сохраняется, аккаунт показывается с пометкой о неподтверждённом состоянии. Ошибка чтения Keychain не означает ни отсутствия, ни истечения учётных данных.

Граница поколений сессии: ответ запроса предыдущей сессии не применяется после выхода — выход очищает удерживаемую сессию до сетевого вызова, а незавершённый вход закрывает свой листенер.

## 3. Баланс и расходы аккаунта

**Вне текущего объёма.** Задача ограничена авторизацией: приложение показывает аккаунт и не запрашивает деньги. Ниже — предложение для следующего этапа, а не действующий контракт. Приложение не вызывает эти маршруты и не показывает ни баланс, ни расходы.

Назначение (следующий этап): получать реальные денежные значения и расходы с сервера, а не вычислять их по локальным журналам агентов. Ответственный: backend.

**Маршруты браузерного account API обнаружены, но успешные JSON-схемы и применимость к desktop-сессии не подтверждены.** Уточнить `/user/profile` и `/usage/stats` вместо создания второго неподтверждённого API. Метод `/v1/usage?days=7`, защищённый API-ключом, не подставляется вместо них. Подтвердить scopes и совместимость с авторизацией по сессии настольного клиента.

**Предложение схемы, не действующий API:**

```json
{
  "account_id": "example-account",
  "as_of": "2026-10-13T12:00:00Z",
  "balance": { "amount_minor": 0, "currency": "USD", "scale": 2 },
  "expenses": {
    "amount_minor": 0,
    "currency": "USD",
    "scale": 2,
    "scope": "account",
    "period_start": "2026-10-01T00:00:00Z",
    "period_end": "2026-11-01T00:00:00Z"
  }
}
```

Вместо целых чисел в минимальных денежных единицах можно выбрать десятичные строки, но контракт должен однозначно задать точность, валюту, отрицательный баланс, округление, отсутствие полей, `null` и числовые пределы. `0` — реальный ноль; отсутствие поля не означает ноль. Указать область аккаунта или ключа, даты UTC ISO-8601, включительность границ периода, часовой пояс расчёта расходов и время актуальности данных. Снимок данных должен быть согласован для одного аккаунта и одного момента времени.

Определить HTTP- и бизнес-семантику: 401 для истёкших или отозванных учётных данных; 403 для ошибок прав или scopes; 429 с Retry-After; 5xx и временные сетевые ошибки; бизнес-ошибки внутри HTTP 200, если используется оболочка ответа. Указать версию схемы и обязательные поля. При сетевой ошибке сохранять последнюю подтверждённую сумму с временем получения и отметкой об устаревании. Без успешного запроса суммы не показываются.

Опрос: опубликовать минимальный интервал, лимиты запросов и правила кэширования/ETag. Если рекомендаций нет, предложение — раз в 60 секунд при активной подтверждённой сессии, не более одного запроса одновременно. При выходе опрос прекращается, старый запрос отменяется, его ответ не принимается. Ручное обновление соблюдает серверные ограничения.

## 4. HTTPS-переход к пополнению

Назначение: открыть официальный браузерный сценарий без создания платежа приложением. Ответственный: backend.

**Подтверждённый URL:** `https://api.wikivibe.dev/purchase`. Публичная документация и router определяют его как пополнение; фактическая навигация проверена без оплаты. Страница требует входа в браузере. Приложение открывает только этот фиксированный HTTPS URL, без токенов или session binding в query. Открытие страницы не подтверждает вход в приложение и не означает выполненный платёж.
